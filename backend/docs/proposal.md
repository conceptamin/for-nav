# for-nav 백엔드 기획서

기준일: 2026-10-24 · 목표 기획 · 기준: [공통 기획서](../../docs/proposal.md)

## 1. 목표와 경계

다국어 채팅에서 상담 요청과 상황을 구조화하고, 사용자가 확인한 정보를 센터로 전달하며 후속 상담·처리 결과를 관리한다. FastAPI/Pydantic 실행 기반은 유지한다. 진단·산재 인정·보험 적용·지급 판단은 하지 않는다.

## 2. 처리 흐름

텍스트 입력 → 필요한 정보 추출·검증 → 상담 상태 갱신 → 부족한 정보에 대한 질문 → 사용자 요약 확인·수정 → 전달 동의 검증 → 접수 → 담당자 응대·상태 변경 → 결과 기록.

LLM은 이해·번역·추가 질문·요약을 맡는다. 접수·권한·조회 성공·상태 전환은 일반 코드가 관리한다. 대화와 별도의 구조화된 상담 상태를 유지하며 추출 정보에 원문·자료 출처를 연결한다. 모름·건너뛰기·불일치를 임의의 값으로 채우지 않는다.

## 3. 필요한 데이터와 API 책임

아래는 설계 항목이며 확정된 스키마나 엔드포인트가 아니다.

| 영역 | 설계할 내용 |
|---|---|
| 인증·권한 | 사용자 본인 상담 접근, 상담사 역할·배정별 접근 |
| 상담 건 | 유형, 요청 요약, 필요한 기본정보, 생성·수정 시점 |
| 대화 | 작성 주체(AI/사용자/상담사), 원문·번역, 질문·수정 이력 |
| 구조화 정보 | 값, 미확인 상태, 근거 발언·자료, 확인 시점 |
| 보험 | 종류, 결과·확인 범위, 출처, 실패·거절·미확인 구분 |
| 동의·인계 | 목적·대상 항목·시점, 전달할 정보 확정, 접수 중복 방지 |
| 처리 | 담당자, 추가 확인 요청, 상태 전환, 연계·종결 결과 |

건강보험 자격, 산재 사업장 관련 정보, 개인보험 가입 내역은 서로 다른 제공 경로·항목을 가질 수 있다. 각 연동의 이용 자격과 외국인 인증을 검증하고, 확인되지 않은 연동은 mock으로 명시한다. 상세 보장 분석은 MVP 밖이다.

## 4. 저장과 외부 전송

센터 인계·후속 응대를 위해 서버 저장이 필요한 목표 설계다. 기존 v1의 무인증·DB 없음·서버 미저장 규칙을 그대로 적용할 수 없다. DB 제품은 아직 선정하지 않는다. 저장 항목·보관기간·삭제·동의 철회·접근 권한을 새 API 계약과 함께 확정한 뒤 구현한다.

일반 로그에는 요청 본문·상담 내용·인증정보·LLM 원문을 남기지 않는다. 외부 LLM 전송은 동의한 필요한 정보로 제한하고 키는 서버 환경 변수로 관리한다. 센터 전달에서 제외한 정보는 전달용 요약 생성 입력에서도 제외한다. 서비스 사용자 정보를 모델 학습에 사용하지 않는다.

## 5. 오류와 검증

- 외부 AI 실패 시 확인된 상담 정보를 보존하고 재시도·수동 입력·센터 요청 경로를 설계한다.
- 보험 조회 실패·인증 불가·부분 조회를 미가입으로 바꾸지 않는다.
- 동의·권한 검사를 서버에서 수행하고 다른 사용자의 상담 조회·수정을 막는다.
- 접수 재시도에서 상담 건이 중복 생성되지 않도록 검증한다.
- 미확인 사실을 생성하지 않는지, 사용자 수정이 다음 질문·요약에 반영되는지 평가한다.
- 긴급 도움 경로가 LLM 응답 성공에 의존하지 않게 하고, 구체적인 감지 기준은 별도 검증한다.
- 테스트는 가짜 LLM·연동으로 실행하고 개발·데모는 합성 데이터만 사용한다.

## 6. 전환 순서

운영·권한·보관 정책 → 상담/인계/보험 상태 API 계약 → Pydantic·OpenAPI·fixtures·소비 코드 동시 변경 → 접수와 후속 응대 구현 → 검증된 보험 연동 추가.

[API v1](../../docs/api-contract.md)과 [이전 phase-02](phase-02.md)는 과거 기획 참조로 남긴다. 이번 개정은 스키마·코드·fixtures를 변경하지 않는다. 구현 전 새 phase에서 인증·저장·실패 복구 완료 기준을 확정한다. 평가 책임은 [모델링 기획](../../modeling/docs/proposal.md)과 나눈다.
