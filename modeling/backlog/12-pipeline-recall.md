# 12. 규칙 + 응급도 모델을 합친 응급 재현율(test)

상태: 완료
의존: 10, 11, backend 06

## 목표
백엔드 06은 `emergency = 규칙 or 모델`로 응급을 판정한다. 응급도 v2 모델만의 test 재현율(10)은 40/49(지금 백엔드 입력)인데, 규칙이 모델이 놓친 응급을 얼마나 메우는지는 재지 않았다. 서빙과 같은 순서(백엔드 규칙 → `predict`)로 test에서 한 번 재서, 실제 서버의 응급 재현율을 기록한다. test를 이 평가에 한 번 더 쓰는 것은 사용자가 승인했다(2026-10-30).

## 범위
- 하는 것
  - `src/fornav_modeling/pipeline.py`: test 행 → 백엔드 `Intake` 모양 dict, 백엔드 `app.rules.triage.triage`를 backend uv 환경에서 subprocess로 부르기(규칙을 다시 적지 않는다), 규칙·보조 점수·모델·규칙 + 모델의 응급 재현율·응급 판정 건수·정밀도
  - `scripts/evaluate.py --model pipeline --round v2`: test를 읽는 유일한 명령에 선택지 하나 추가
  - 입력 모양 두 가지(10과 같음): full(통증·의식·나이대·성별·손상 여부를 앎), backend(부위·증상만)
  - `tests/test_pipeline.py`: 합성 행으로 변환·지표·한 번만 실행, backend 규칙 호출
- 하지 않는 것
  - 모델·임계값·규칙 변경, test 오류 분석(어떤 행을 놓쳤는지 보지 않는다), `backend/` 코드 수정

## 입력·출력
- 입력: `data/test/triage_test.parquet`(해시 확인), `models/*/v2/`, `../backend/app/rules/triage.py`
- 출력: `reports/pipeline_v2_test.{json,md}`

## 완료 기준
- [x] `uv run ruff check . && uv run ruff format --check .`, `uv run pytest` 통과
- [x] test 1회. 규칙만, 규칙 + 보조 점수(모델 없음), 모델만, 규칙 + 모델을 입력 모양별로 응급 재현율·응급 판정 건수 분자·분모로 기록
- [x] "모델만" 값이 10의 test 결과(full 42/49, backend 40/49)와 같다(같은 모델·임계값인지 확인)

## 결과
- 실행(2026-10-30)
  - `uv run ruff check . && uv run ruff format --check .` → `All checks passed!`, `73 files already formatted`
  - `uv run pytest` → `186 passed`(기존 181 + `test_pipeline.py` 5)
  - `uv run python scripts/evaluate.py --model pipeline --round v2` → 1.5초. `reports/pipeline_v2_test.{json,md}`. 규칙은 main의 backend(06 병합 후) `app.rules.triage.triage`
- **최종: test(254건, 실제 응급 49건)**. 자유 입력 없음 — 규칙은 버튼 조합 분기(숨 가쁨, 가슴 + 통증, 눈 + 화학물질)만 지난다

| 판정 | 응급 재현율 | 응급으로 본 건수 | 응급 판정 정밀도 |
|---|---|---|---|
| 규칙만 | 17/49 (34.7%) | 29/254 | 17/29 |
| 규칙 + 보조 점수(모델 없음 = 프론트 오프라인 대체) | 17/49 (34.7%) | 29/254 | 17/29 |
| 모델만, full | 42/49 (85.7%) | 129/254 | 42/129 |
| **규칙 + 모델, full (서빙)** | **42/49 (85.7%)** | 130/254 | 42/130 |
| 모델만, backend | 40/49 (81.6%) | 129/254 | 40/129 |
| **규칙 + 모델, backend (서빙)** | **40/49 (81.6%)** | 129/254 | 40/129 |

- 읽는 법
  - **규칙이 모델 위에 더하는 응급은 0건이다.** 규칙이 잡는 응급 17건은 모델도 모두 잡는다. 서버의 응급 재현율은 모델만의 재현율과 같고, 목표 95%에 못 미친다(full 7건, backend 9건 놓침). 규칙이 더하는 것은 full에서 비응급 1건을 응급으로 보는 것뿐이다
  - **모델이 없으면(서버 실패 → 프론트 브라우저 규칙) 응급 재현율이 17/49(34.7%)다.** 보조 점수는 이 데이터에서 하나도 더 잡지 않는다(가산 항목인 출혈·화상·마비·화학물질 조합이 주증상 매핑에 거의 없다)
  - "모델만" 값이 10의 test 결과(full 42/49, backend 40/49, 응급 판정 129/254)와 같다. 같은 모델·임계값으로 평가했다
- 결정 사항
  - 규칙은 backend 코드를 subprocess로 부른다. 모델링 환경에는 pydantic이 없고, 규칙을 모델링에 다시 적으면 백엔드와 어긋날 수 있다. 입력·출력은 표준 입출력 JSON으로만 넘겨 test 행이 파일로 남지 않는다
  - 백엔드 규칙에는 부위·증상만 넘긴다. 규칙은 응급도 입력 필드(통증 점수 등)를 쓰지 않으므로(backend 10) 입력 모양과 관계없이 같다
  - 자유 입력은 넣지 않았다. 원본 주증상은 의료진이 쓴 문장이라 사용자 자유 입력으로 볼 수 없다. 실제 사용자가 "의식", "경련" 같은 말을 쓰면 키워드 규칙이 더 잡을 수 있지만 이 데이터로는 잴 수 없다

## 메모
- 모델이 놓치는 응급을 줄이려면 모델 쪽(임계값을 더 낮추기, 데이터 보강) 또는 규칙 쪽(버튼 조합 규칙 추가)을 바꿔야 한다. 어느 쪽이든 test를 다시 쓰지 않고 valid로 정한 뒤 새 라운드로 평가한다. 어떤 행을 놓쳤는지는 test로 보지 않는다
- 프론트 오프라인 대체의 재현율(34.7%)은 서버 실패 시 안전 문제다. 프론트에서 서버 실패 때 보수적으로 안내하는 방법(예: 응급 여부를 확신할 수 없다는 안내)은 frontend·backend와 정할 일이다
